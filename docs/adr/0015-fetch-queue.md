# ADR 0015: 取得のキューを Rust で実装し、タスクを「呼ぶと Future を返す関数」として扱う

ステータス: 採択

## 文脈

作品のメタデータと話の取得を実装する前に、取得のキューを作る。
ADR 0004 で、ドメインごとのキュー、待ち時間のタスク、積み直しによる再試行、キューの削除によるキャンセルを決めた。
この ADR では、それを実装する形と、ADR 0004 で決めていなかった再試行の上限、レート制限、クロールの間隔、fetch all を繰り返し押したときの扱いを決める。

Promise や Future を作った時点で処理が始まる環境では、それをキューに積むと、積んだ時点で取得が始まり、間隔の制御が効かない。
クローラーの `error` レコード（ADR 0005）には、レート制限のときにいつまで待てばよいかの情報がない。

## 実装すること

- キューは Rust（tokio）で実装する。アプリと同じ寿命で動き、WebView の読み直しの影響を受けない
- キューに積むタスクは「呼ぶと Future を返す関数」とする。積んだ時点では何も実行されず、キューが取り出して呼んだときに始まる
- キューは中身を知らない。取得のタスクと待ち時間のタスクを区別せず、どちらも同じタスクとして扱う。キューが持つ操作は、末尾に積む、先頭に積む、全て破棄する、だけとする
- ドメインごとに 1 本のキューを持つ。ドメインは取得する URL のホスト名とする（同じ運営元の別ホストをまとめることは、いまは考えない）
- 各ドメインのキューは、タスクを 1 つ取り出して実行の側に渡し、そのタスクが終わるのを待ってから次を取り出す。これにより、同じドメインのタスクは順に、異なるドメインのタスクは並列に実行される。実行の側の並列数に上限は設けない
- 取得のタスクを積むときは、取得と、その後に 5 秒待つタスクを 1 組として末尾に積む。積み直すときも同じ組で積む
- 取得のタスクは、ADR 0005 に従うクローラーを子プロセスとして起動する（ADR 0004）
- 再試行するかどうかは、取得のタスクが自分で決め、自分で積み直す。キューは結果を見ない
  - `server_error` と `network` のときは、取得と待ちの組を末尾に積み直す。積み直しは 3 回までとし、4 回目の失敗であきらめる
  - `rate_limited` のときは、そのドメインのキューの先頭に「指定の日時まで待つタスク」を積み、その後ろに失敗した取得を積み直す。先頭に積むのは、後ろに並んでいる取得が待たずに同じサーバーへ送られるのを防ぐためである。この積み直しは 3 回に数えない
  - それ以外の `kind`（`unsupported_url`、`not_found`、`forbidden`、`http_error`、`parse_error`）では積み直さない
  - 再試行の回数は、タスクが作られるときに閉じ込めて持つ
- レート制限で待つ日時は、クローラーの `error` レコードに任意の項目 `retryAfter`（UTC からの時差を含む ISO 8601 の日時、または null）を足して受け取る。クローラーは HTTP の `Retry-After` を日時に直して入れる。項目の追加なので `v` は上げない（ADR 0005）。`retryAfter` がないときは 60 秒待つ
- fetch all を押したときは、全てのドメインのキューを破棄してから、取得すべきタスクを積み直す。続けて押しても、同じタスクが重複して積まれることはない
- 画面のトップの取得時間の目安（ADR 0011）は、1 回の取得を 5 秒として計算するよう揃える

## 実装しないこと

- 同じ運営元の別ホスト（`ncode.syosetu.com` と `novel18.syosetu.com` など）を 1 本のキューにまとめることはしない
- キューの中身を保存しない。アプリを終了すると積んでいたタスクは消える。取得済みかどうかは SQLite に残るため、起動し直した後に fetch all で積み直す
- 実行中のタスクを途中で止めることはしない。キューを破棄しても、実行中の取得と待ちは最後まで動く（ADR 0004）
- クロールの間隔を画面で設定できるようにはしない
- キューの中のタスクに識別子を付けて重複を検査することはしない

## テスト設計

- キューの単体テストは、tokio の時間を止めた状態（`tokio::time::pause`）で、中身を知らない偽のタスクを使って行う
  - 同じドメインのタスクが積んだ順に 1 つずつ実行され、前のタスクが終わるまで次が始まらないこと
  - 異なるドメインのタスクが並列に実行されること
  - 積んだ時点ではタスクが呼ばれないこと
  - 待ち時間のタスクが、ほかのタスクと同じように順番どおりに処理されること
  - 先頭に積んだタスクが、すでに並んでいるタスクより先に実行されること
  - 破棄すると、まだ取り出されていないタスクが実行されないこと。実行中のタスクは最後まで動くこと
- 取得のタスクの単体テストは、クローラーの代わりに結果を返す偽物を使って行う
  - 成功すると積み直さないこと
  - `server_error` と `network` では末尾に積み直し、3 回積み直した後の失敗であきらめること
  - `rate_limited` では先頭に待ちと取得を積み、`retryAfter` の日時まで待つこと、`retryAfter` がなければ 60 秒待つこと、回数に数えないこと
  - 積み直さない `kind` では積み直さないこと
  - 積むときと積み直すときに、取得と 5 秒の待ちが 1 組で積まれること
- fetch all を続けて押しても、キューに同じタスクが重複しないことをテストする
- 取り込みを実装するときに、`retryAfter` を含む `error` レコードを JSON Schema で検証できることをテストする

## トレードオフ

- タスクを関数として持つため、キューの中身を見て何が積まれているかを知ることはできない。その代わり、キューは取得にも待ちにも同じ仕組みで使える
- 5 秒の間隔では、未取得の話が数千件あると取得に数時間かかる。その代わり、相手のサーバーに負担をかけにくい
- 実行の側の並列数に上限がないため、ドメインの数だけ子プロセスが同時に動く。いまはドメインが数個なので問題にならない
- ホスト名ごとにキューを分けるため、同じ運営元の別ホストへは並列にリクエストが送られる
- `retryAfter` を使うにはクローラーの対応が要る。対応するまでは、レート制限のたびに 60 秒待つ
- fetch all を押すたびにキューを作り直すため、押した時点で待っていた順番は失われる
