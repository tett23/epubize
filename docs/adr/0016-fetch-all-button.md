# ADR 0016: fetch all のボタンで購読の全作品の目次を積み、取得の結果はまだ保存せず画面に知らせる

ステータス: 採択

## 文脈

取得のキュー（ADR 0015）ができたので、トップの fetch all のボタンをつなぐ。
話の取得には、目次を保存して、どの話が未取得かを知る必要があるが、SQLite のスキーマはまだない。
クローラーの実行ファイルの場所は、設定画面か PATH から探すとした（ADR 0004）が、設定画面はまだない。

実際のアプリで確かめたところ、取得の最中に fetch all を押し直すと、取得の後ろにあった待ちが破棄され、同じドメインへの次の取得が直後に送られた。
キューは中身を知らないため、キューの側で待ちだけを残すことはできない。

## 実装すること

- fetch all を押すと、全てのキューを破棄し、`novels.json` で購読している全作品の `toc` の取得を積む（ADR 0014、ADR 0015）
- 積み直すときは、各ドメインの先頭に取得の間隔（5 秒）の待ちを 1 つ置く。破棄で消えた待ちの代わりとし、実行中だった取得と、積み直した最初の取得の間を空ける
- クローラーの実行ファイルは、設定画面ができるまでの仮の方法として、環境変数 `EPUBIZE_CRAWLER` で指定する。指定がなければ fetch all を押せないようにし、画面に理由を表示する
- 取得が終わるたび（成功、またはあきらめたとき）に、Tauri のイベント `fetch-done` でコマンド、URL、失敗の理由を画面に送る。画面はトップに新しい順に 20 件まで表示する
- 画面はキューに残っているタスクの数を 1 秒ごとに読み、表示する。取得と待ちの両方を数える

## 実装しないこと

- 取得した結果は保存しない。SQLite のスキーマを作るときに、`fetch-done` の代わりに保存する処理をつなぐ
- 話と挿絵の取得は積まない。目次を保存できるようになってから積む
- fetch all metadata のボタンは、いまはつながない。目次の取得が fetch all と同じになるため
- PATH からクローラーを探すことはしない。既定の実行ファイルの名前を決めると、非公開のリポジトリの名前を公開のコードに書くことになるため
- 取得の結果をアプリの再起動の後まで残すことはしない

## テスト設計

- `src-tauri/src/fetch/mod.rs` で、fetch all を続けて呼んでも重複しないこと、最初の取得が先頭の待ちの後に始まること、取得の最中に呼び直しても、実行中の取得の終わりから間隔の分だけ空いて次の取得が始まることをテストする。最後のテストは、先頭の待ちを外すと失敗することを確かめた
- 偽のクローラー（応答に数秒かかり、特定の URL では `server_error` を返すシェルスクリプト）を `EPUBIZE_CRAWLER` に指定して debug ビルドの `.app` を起動し、computer-use で次を確かめた
  - fetch all で、異なるドメインの取得が同時に始まり、同じドメインの取得は前の取得の終わりから 5 秒空くこと
  - `server_error` の作品は 3 回積み直された後にあきらめ、画面に赤字で表示されること。キューの数が 0 に戻ること
  - 取得の最中に押し直しても、同じドメインへの次の取得が前の取得の終わりから 5 秒空くこと

## トレードオフ

- 結果を保存しないため、いまの fetch all は相手のサイトにアクセスするが、得たものを使わない。保存の実装までは、押すのは動作の確認のときだけにする
- 先頭に待ちを置くため、fetch all の最初の取得は押してから 5 秒後に始まる
- クローラーの場所を環境変数で渡すため、Finder などから起動したアプリではクローラーを使えない。設定画面を作るまでの制約とする
- キューの数に待ちも含まれるため、残りの取得の数のおよそ 2 倍が表示される
