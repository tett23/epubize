# ADR 0013: SQLite のマイグレーションを rusqlite と自前の仕組みで行い、起動時に自動で適用し、mise のタスクからも実行する

ステータス: 採択

## 文脈

データは epubize の SQLite に持ち、置き場所は Tauri のアプリ用データ領域とする（ADR 0003）。
スキーマを作る前に、スキーマを変えていく仕組みを決める。
データベースのファイルが消えていても、起動するだけで使える状態に戻したい。
リポジトリにはタスクランナーがなかった。

## 実装すること

- SQLite は rusqlite（`bundled`）で扱う。SQLite をアプリに同梱してビルドし、OS の SQLite の版に左右されないようにする
- マイグレーションは `src-tauri/migrations/NNNN_name.sql` に置く。`NNNN` は 1 からの連番の版、`name` は snake_case とする
  - `build.rs` が版の順に読み、`include_str!` でアプリに埋め込む
  - 名前の形が違うファイルや、版が 1 からの連番になっていないファイルがあれば、ビルドを止める
- 適用済みの版は `PRAGMA user_version` に持つ。別の管理用のテーブルは作らない
- 未適用のマイグレーションを版の順に適用する。1 つのマイグレーションは 1 つのトランザクションで適用し、失敗したら変更を戻して版を進めない
- データベースの版がアプリの知っている最新の版より新しいときは、適用せずにエラーにする
- 接続ごとに `foreign_keys` を有効にし、`journal_mode` を WAL にする
- アプリは起動時（`setup`）にデータベースを開き、未適用のマイグレーションを全て適用する。ファイルがなければディレクトリごと作るため、消えていた場合は全てのマイグレーションが流れる。失敗したら起動を止める
- データベースのパスは `<データ領域>/com.github.tett23.epubize/epubize.sqlite3` とし、アプリと CLI で同じ関数（`db::default_path`）から決める。識別子が `tauri.conf.json` と一致することをテストで確かめる
- CLI `src-tauri/src/bin/migrate.rs` を置く。コマンドは `up`、`status`、`new <name>`、`reset` とし、パスは `--db`、環境変数 `EPUBIZE_DB`、既定の場所の順に決める
- タスクランナーは mise とし、`mise.toml` に `db:migrate`、`db:status`、`db:new`、`db:reset` を置く
- バイナリが二つになるため、`Cargo.toml` の `default-run` を `epubize` にする

## 実装しないこと

- 適用を取り消す down のマイグレーションは作らない。戻すときは、戻す内容の新しいマイグレーションを足す
- コミット済みのマイグレーションの変更を検査することはしない。適用済みのマイグレーションを書き換えても、既存のデータベースには反映されない
- この ADR ではスキーマ（作品、目次、話、挿絵のテーブル）を作らない。スキーマは取り込み（ADR 0005）を実装するときに決める
- マイグレーションの前にデータベースのバックアップは取らない
- mise で Node.js や pnpm などのツールの版を固定することは、この ADR ではしない

## テスト設計

- `src-tauri/src/db/migrate.rs` の単体テストで、次を確かめる
  - 新しいデータベースに全てのマイグレーションが適用されること
  - 未適用のものだけが適用されること、最新なら何もしないこと
  - 失敗したマイグレーションの変更が残らず、版が進まないこと
  - データベースの版がアプリより新しいとエラーになること
  - 埋め込んだマイグレーションの版が 1 からの連番であること
  - `new` が付けるファイル名が最新の版の次になること、snake_case でない名前を拒むこと
- `src-tauri/src/db/mod.rs` の単体テストで、ディレクトリとファイルがなくても作って全て適用すること、消したファイルを開き直すと作り直して全て適用すること、`foreign_keys` と WAL が有効になること、識別子が `tauri.conf.json` と一致することを確かめる
- 確認用のマイグレーションを置いて、次を手で確かめた（確認用のマイグレーションはコミットしない）
  - mise の各タスク（`db:status`、`db:new`、`db:migrate`、`db:reset`、不正な名前の `db:new`）が期待どおりに動くこと
  - アプリを起動するとデータベースが作られて適用されること、ファイルを消して起動し直すと作り直されること
  - 版が飛んだファイルを置くとビルドが止まること

## トレードオフ

- 既製のマイグレーションのライブラリより実装する量が増える。その代わり、依存が少なく、適用の手順を全て把握できる
- `user_version` だけで版を持つため、どのマイグレーションをいつ適用したかの記録は残らない
- 起動時に自動で適用するため、利用者が意識せずにスキーマが変わる。その代わり、アプリを更新しただけで使える
- タスクランナーのために、開発環境に mise が必要になる
- マイグレーションの CLI は Tauri のクレートの中のバイナリなので、初回の実行ではアプリ全体のビルドを待つ
