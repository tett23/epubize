# ADR 0004: クロールの実行をドメインごとのキューで管理し、頻度・再試行・キャンセルを epubize が担う

ステータス: 採択

## 文脈

クローラーはリクエストの間隔を空けず、再試行もしない（クローラー側の決定）。
クロールの頻度、失敗時の再試行、途中で止めることは、呼び出し側の epubize が管理する。
複数のサイトの作品を扱うため、サイトごとに独立して進められるようにしたい。

## 実装すること

- クロールのタスク（目次の取得、各話の取得、挿絵の取得）を、ドメインごとに 1 本ずつ用意したキューに積む
- 実際にクロールするキューは複数本とし、ドメインごとに並列で処理する。同じドメインのタスクは、そのキューの中で順に処理する
- 実際にクロールするキューでは、クロールのタスクの間に「適当な秒数を待つ Promise」を挟む。クロールのタスクと待つタスクは Promise として区別せず、どちらも処理すべきタスクとして同じように扱う
- 失敗したクロールは、タスクとしてキューに積み直すことで再試行する。積み直すかどうかは、クローラーが返すエラーの種類（ADR 0005）で判断する
- キャンセルは、キューのタスクを全て削除することで行う
- クローラーは子プロセスとして起動する。実行ファイルの場所は、設定画面で指定するか、PATH から探す
- クローラーは epubize に同梱しない

## 実装しないこと

- 同じドメインへのリクエストを並列に送ることはしない
- クローラー側に頻度や再試行の設定を渡すことはしない
- Tauri の sidecar の仕組みでクローラーを同梱することはしない

## テスト設計

- 方針の決定であり、この時点ではコードを伴わないため、テストはない
- キューを実装するときに、次をテストする
  - 同じドメインのタスクが順に処理され、異なるドメインのタスクが並列に処理されること
  - 待つタスクがクロールのタスクと同じように順番どおりに処理されること
  - 失敗したタスクが積み直されること、積み直さない種類のエラーでは積み直されないこと
  - キューを全て削除すると、以降のタスクが処理されないこと

## トレードオフ

- 待ち時間をタスクとして積むため、キューの長さが実際のリクエストの数より多くなる。その代わり、待ちとクロールを同じ仕組みで扱える
- 処理中のタスクはキューの削除では止まらない。止めるには、実行中の子プロセスを終了させる必要がある
- クローラーを同梱しないため、利用者がクローラーを別に用意する必要がある
